# Эталонная архитектура контейнерного браузера

Читайте этот файл при первичной установке или ремонте окружения. Обычная работа после
настройки описана в `SKILL.md`.

## Схема

```text
человек ── SSH tunnel или HTTPS + auth ── noVNC :6080
                                                │
                                             x11vnc
                                                │
агент ── localhost хоста :9223 ── CDP forward ── Chrome :9222
                                                │
                                         /data/profile
```

Chrome, экран и VNC живут в одном контейнере. Каталог `/data/profile` смонтирован с хоста
и переживает перезапуск. Человек и агент используют одну сессию, поэтому переносить cookies
и пароли не требуется.

Для контейнерного SaaS браузер должен создавать **хостовый broker**, а не пользовательский
контейнер. Не передавайте контейнеру `/var/run/docker.sock`: это равносильно административному
доступу к хосту. Broker обязан получить проверенную identity от оркестратора, создать отдельные
container и profile volume, а затем разрешить HTML и WebSocket только тому же пользователю.

## Установка из шаблонов

Скопируйте `assets/Dockerfile`, `assets/entrypoint.sh` и `assets/compose.yaml` в отдельный
служебный каталог проекта. Каталог данных создайте **вне Git**:

```bash
install -d -m 700 /srv/browser-handoff/data
export BROWSER_DATA_DIR=/srv/browser-handoff/data
docker compose build
docker compose up -d
```

Шаблон публикует noVNC и CDP только на loopback хоста. Проверьте это до передачи ссылки:

```bash
docker compose ps
curl --fail http://127.0.0.1:9223/json/version
ss -lnt | grep -E '127\.0\.0\.1:(6080|9223)'
```

Любая строка `0.0.0.0:6080` или `0.0.0.0:9223` на хосте — блокирующая ошибка.

## Доступ человека

### Вариант A: SSH-туннель

Предпочтителен, если у владельца есть SSH-доступ:

```bash
ssh -N -L 6080:127.0.0.1:6080 user@server
```

После этого владелец открывает локально:

```text
http://127.0.0.1:6080/vnc.html?autoconnect=1&resize=scale
```

### Вариант B: HTTPS reverse proxy

Подходит для телефона и пользователей без SSH. Прокси обязан:

- завершать TLS;
- проверять существующую пользовательскую сессию или отдельную сильную аутентификацию;
- проксировать WebSocket upgrade для noVNC;
- не отдавать CDP;
- иметь короткий срок жизни ссылки и журнал успешных входов без query-string и cookies.

Проверьте оба канала отдельно: обычный запрос к `vnc.html` и WebSocket noVNC. Частая ошибка —
закрыть авторизацией HTML, но оставить WebSocket доступным без неё. До выдачи ссылки запрос
без cookie должен получить `401/403` либо редирект на штатный login; запрос пользователя B
к браузеру пользователя A также должен получить отказ.

Случайный URL не заменяет аутентификацию. Basic Auth допустим только поверх HTTPS и с
уникальным паролем из секрет-стора; пароль не коммитится и не пишется в командную строку.

## Подключение агента

Python + Playwright:

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.connect_over_cdp("http://127.0.0.1:9223")
    context = browser.contexts[0]
    page = context.new_page()
    try:
        page.goto("https://example.invalid/", wait_until="domcontentloaded")
        # Подготовить черновик. Финальное внешнее действие — после подтверждения.
    finally:
        page.close()
        browser.close()  # отключает Playwright, но не закрывает контейнерный Chrome
```

Не используйте `launch_persistent_context` поверх уже работающего профиля: это второй
писатель. Не обращайтесь к `context.cookies()` ради экспорта и не записывайте storage state.

## Файлы

Для загрузки больших файлов не гоните содержимое через удалённый CDP. Безопасные варианты:

1. смонтировать в контейнер отдельную read-only папку конкретной задачи;
2. `docker cp` одного согласованного файла во временную папку контейнера;
3. после завершения удалить временную копию.

Не монтируйте `/root`, `$HOME`, секрет-стор или весь рабочий каталог агента.

## Жизненный цикл

- Поднимайте контейнер под задачу; вход, 2FA и капчу всегда выполняет владелец через noVNC.
- После сообщения владельца «готово» агент работает через CDP, не открывая и не извлекая
  секреты из формы входа.
- Перед остановкой убедитесь, что владелец отключился и другой агент не использует CDP.
- Пока продолжается согласованная рутинная автоматизация, поддерживайте контейнер здоровым
  и перезапускайте его с тем же profile volume. Сайт сам определяет срок действия входа.
- Задайте явный срок бездействия по условиям среды (например, сутки или неделю), сообщите
  его владельцу и только после него останавливайте контейнер. Не удаляйте volume профиля.
- Обновление Chrome сначала проверяйте на копии пустого профиля.
- Удаление профиля означает выход из всех аккаунтов и требует отдельного подтверждения.

## Реакция на инцидент

Если noVNC или CDP были доступны из интернета без надёжной аутентификации:

1. остановите контейнер и закройте порт;
2. сохраните только технические журналы без профиля и cookies;
3. сообщите владельцу период доступности;
4. завершите активные сессии на затронутых сайтах и смените пароли/токены по решению владельца;
5. создайте новый чистый профиль.
